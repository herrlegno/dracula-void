# Contributing

Thanks for contributing to Dracula Void.

## Development setup

1. Clone the repository.
2. Open it in IntelliJ IDEA as a Gradle project.
3. Let Gradle import the project configuration.

## Project structure

- `.release-please-manifest.json` - release-please's version manifest.
- `CHANGELOG.md` - release notes generated by release-please in the automated release PR flow.
- `release-please-config.json` - release-please configuration for versioning, changelog sections, and synced files.
- `upstream/` - vendored Dracula Colorful upstream snapshots.
- `resources/theme/DraculaVoid.xml` - bundled editor scheme.
- `resources/theme/DraculaVoid.theme.json` - primary UI theme.
- `resources/theme/IslandsDraculaVoid.theme.json` - Islands-based UI theme.
- `resources/META-INF/plugin.xml` - plugin metadata and theme registration.
- `scripts/sync-dracula-base.sh` - helper for refreshing upstream snapshots.
- `version.txt` - canonical release-please version file mirrored into plugin metadata.

## Building and testing

The project uses Gradle `9.1.0` and the IntelliJ Platform Gradle plugin `2.12.0`.

Build the plugin ZIP:

```bash
./gradlew buildPlugin
```

Run the plugin in a sandbox IDE:

```bash
./gradlew runIde
```

The packaged plugin ZIP is written to `build/distributions/`.

Verify compatibility against JetBrains' recommended IDE matrix:

```bash
./gradlew verifyPlugin
```

## Syncing upstream

Refresh the vendored Dracula Colorful baseline with:

```bash
./scripts/sync-dracula-base.sh
```

This updates the files in `upstream/` so local changes stay easy to compare against upstream.

## Pull requests

- Pull requests that modify the theme should include before-and-after screenshots so changes are easy to review.
- Pull request titles must follow the Conventional Commits format; GitHub Actions enforces this on every PR.
- `feat`, `fix`, `perf`, `revert`, and `!` titles feed the automated release bump after squash merge.

Example titles:

```text
feat(theme): add darker tool window backgrounds
fix(editor): restore selection contrast in markdown
chore(build): update IntelliJ platform plugin version
```

## CI and releases

- GitHub Actions runs CI on pushes to `main` and on pull requests.
- GitHub Actions also validates pull request titles against Conventional Commits so squash merges keep semantic history.
- CI builds the plugin, validates the plugin project configuration, and verifies compatibility.
- When you want to cut a release, run the `Create Release PR` workflow against `main`; release-please opens or updates a release PR that bumps `version.txt`, syncs `gradle.properties`, `resources/META-INF/plugin.xml`, and the README badge, and refreshes `CHANGELOG.md`.
- The release PR title is `chore(release): <version>` so it still satisfies the PR title policy under squash merges.
- `release-please-config.json` pins the initial release to `1.0.0`, so the first release PR boots from the current plugin version without a custom changelog script.
- Merging that release PR triggers `Auto Release`, which lets release-please create tag `v<major>.<minor>.<patch>` and the GitHub Release before the workflow publishes to JetBrains Marketplace and uploads the ZIP artifact.
- `.github/workflows/release.yml` remains available as a manual fallback release path for the current ref.

Required GitHub secrets for releases:

- `PUBLISH_TOKEN` - JetBrains Marketplace publishing token.
- `CERTIFICATE_CHAIN` - signing certificate chain in PEM format.
- `PRIVATE_KEY` - signing private key in PEM format.
- `PRIVATE_KEY_PASSWORD` - password for the private key.

Optional GitHub secret:

- `RELEASE_PLEASE_TOKEN` - personal access token used by release-please when you want CI and other workflows to trigger from its release PRs and tags. If unset, the workflows fall back to `GITHUB_TOKEN`.
